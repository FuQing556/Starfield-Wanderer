## 4. 非资源景观：四种标准 Prefab

### 4.1 A 类：地面细节（可直接踩过）

适用：小花、草簇、落叶、泥点、细小碎石。

```text
Scenery_Midland_GrassTuft_A
└─ Visual (SpriteRenderer)
```

配置：

- 无 Collider2D。
- 无 `YSortGroup`，除非图像明显高于角色脚面。
- Sorting Layer 使用 `Ground` 或当前地面细节专用层；Order 比正式地面高 1～3 即可。
- 不要给每一簇草挂 Animator。若素材没有动画就保持静态。
- 成片效果靠少量不同变体、翻转和疏密变化，不靠上千个重叠物体。

### 4.2 B 类：可穿过但需要前后遮挡的高景物

适用：不阻挡玩家的高草、旗帜、细小灌木、装饰柱。

```text
Scenery_Midland_Flag_A
├─ Visual (SpriteRenderer，Player)
└─ SortPoint (空物体，放在物体真实落地点)
```

根物体挂 `YSortGroup`，明确拖入 `Visual` 和 `SortPoint`。没有 Collider2D。角色走到其上方时景物应遮住角色，走到其下方时角色应遮住景物。

### 4.3 C 类：实体障碍景物

适用：景观树、景观石、栅栏、营帐、建筑。

```text
Scenery_Midland_Tree_A
├─ Visual (SpriteRenderer，Player)
├─ SortPoint (树根/落地点)
└─ FootprintCollider (BoxCollider2D 或 CapsuleCollider2D)
```

配置原则：

- `YSortGroup` 只看 `SortPoint`，不要拿透明格子的 Bottom Center 当脚底。
- ★ Visual 的 **Sorting Layer 必须用 `Player`**（不是 Objects）：角色在 Player 层，YSort 只改 Order 不改层，跨层时「层 > 序」Order 无效，景物会被角色永远盖住。这里的 Player 是 SpriteRenderer 上的 Sorting Layer，与下方物理 Layer 无关。
- Collider 只包住树干、石头底座或建筑墙脚，不包树冠和整张图片。
- 碰撞体宁可略小，不要严丝合缝；目标是防止穿过树干，而不是让移动卡手。
- 默认放在 `Default` Layer。当前视野遮挡默认检查 `Default + Enemy`；若擅自新建 `WorldObstacle` 层，就必须同步检查玩家移动、攻击、子弹和视野所有 LayerMask，V1.0 不建议这样做。
- 禁止使用自动生成的像素轮廓 PolygonCollider2D。

### 4.4 D 类：宝箱等可交互物

正式宝箱继续使用：

```text
Container_Chest
├─ Visual
├─ SortPoint
└─ FootprintCollider
```

当前 `Container_Chest.prefab` 已换上正式木铁宝箱图片。现有 `BoxCollider2D` 是 Trigger，不能阻挡玩家；而 `Chest` 脚本实际按距离和 `InteractableRegistry` 判断交互，并不依赖 `OnTriggerEnter2D`。若希望宝箱实体挡路，建议把当前碰撞体缩到箱体底部并改成非 Trigger；如果后续确实需要独立触发区，则使用两个碰撞体：小的非 Trigger 脚印碰撞 + 大的 Trigger 交互区，二者职责不得混淆。

宝箱还需要：

- `YSortGroup` + 手放 `SortPoint`。
- SpriteRenderer 的 Sorting Layer 使用 `Player`（原因同上：需与角色同层才能按 Y 遮挡）。
- `Chest.storage`、`Chest.chestUI` 等引用在 Inspector 检查，不要靠新代码自动寻找。
- 当前 `Chest` / `ChestUI` 中还保留旧的 `AddComponent` 兜底写法，这是历史代码，不要把这种写法复制给新系统；V1.0 期间也不要顺手重构它。

### 5.1 中土第一版布局

中土定位是安全、易懂、用于教学和补给的出生区，不需要堆满复杂机制：

1. 出生点周围保留一块明显空地，镜头内不要刷资源树、矿石或敌人。
2. 以出生点为中心做一条主路和两条短支路，路宽至少允许玩家与一只敌人错身。
3. 人类营地靠近主路，使用规则排列、宝箱、栅栏和建筑，显得稳定有秩序。
4. 哥布林营地放在偏远支路或林边，使用不规则排列、木桩、碎石和破损建筑，轮廓更杂乱。
5. 两个营地之间留出战斗缓冲区，不让怪物出生点、资源点和宝箱互相重叠。
6. 四个方向的区域入口先用路口、路牌、少量异色植被或一只弱化区域怪提示，不急着建完整传送门。
7. 手工景物放好后，再把 `WorldSpawner` 的大矩形拆成多个小矩形，绕开道路、营地、出生点和固定宝箱。

### 5.2 密度与性能

- 一屏建议只有 1～3 个视觉焦点，周边再散布小型地面细节。
- 大树和建筑不要等距排成棋盘，使用 2～5 个小簇，中间留可行走缺口。
- 同一张景观 Sprite 可用 `flipX` 和轻微位置错落增加变化；不要用非整数任意缩放破坏像素风。
- 静态景观不挂 Update 脚本、不挂 Rigidbody2D、不挂无意义 Animator。
- V1.0 不做自动景观生成、对象池或复杂分区加载。先保证布局好看、可走、不卡手。

### 5.3 景观验收

- 玩家走到景物上方/下方时遮挡关系正确。
- 玩家不能穿过树干、巨石和建筑底座，但不会被树冠边缘卡住。
- 箭矢与视野能被实体景物合理遮挡。
- 不可采集景物不会出现血量、三阶段、掉落或采集提示。
- 出生点、主路、营地入口、宝箱前方没有随机资源堵路。
- 场景 Hierarchy 中没有散落的 `TilesetNature_30 (1)...(99)`。

## 6. 音效与音乐完整配置计划

### 6.1 当前审计结果

- `Assets/Audio` 目录存在但为空。
- 项目中没有正式音频文件、AudioMixer、AudioSource 或 AudioClip 引用。
- 脚本中也没有 `PlayOneShot` / `PlayClipAtPoint` 接入。
- 所以这不是“补几个音效”，而是从零建立一条最小音频管线。

### 6.2 文件夹结构

```text
Assets/Audio/
├─ Mixers/
│  └─ MasterAudioMixer.mixer
├─ Music/
│  ├─ Midland/
│  └─ Battle/
├─ Ambience/
│  ├─ Midland/
│  └─ Weather/
└─ SFX/
   ├─ Player/
   │  ├─ Attack/
   │  ├─ Movement/
   │  └─ Damage/
   ├─ Enemies/
   │  ├─ Human/
   │  └─ Shared/
   ├─ Combat/
   │  ├─ Impact/
   │  └─ Projectile/
   ├─ World/
   │  ├─ Harvest/
   │  ├─ Pickup/
   │  └─ Chest/
   └─ UI/
      ├─ Click/
      ├─ Panel/
      └─ Feedback/
```

命名使用：`SFX_<系统>_<动作>_<变体>`、`BGM_<区域>`、`AMB_<区域>_<环境>`。

示例：`SFX_Player_Stardust_Cast_A.wav`、`SFX_Combat_Arrow_Hit_A.wav`、`BGM_Midland.ogg`。

### 6.3 AudioMixer

创建一个 `MasterAudioMixer`，组结构：

```text
Master
├─ Music
├─ Ambience
├─ SFX
│  ├─ Player
│  ├─ Enemy
│  └─ World
└─ UI
```

暴露参数：

- `MasterVolume`
- `MusicVolume`
- `AmbienceVolume`
- `SfxVolume`
- `UiVolume`

V1.0 可以没有音量设置面板，但 Mixer 和分组必须先正确，避免后续所有音量写死在每个 AudioSource 上。

### 6.4 导入设置

短 SFX：

- 优先 WAV。
- Load Type：`Decompress On Load`。
- Compression Format：PCM 或 ADPCM。
- Preload Audio Data：开。
- Load In Background：关。
- 世界定位音效可勾 `Force To Mono`；UI 音效不用。

音乐/长环境音：

- 优先 OGG。
- Load Type：`Streaming`。
- Compression Format：Vorbis，Quality 先用 50%～70%。
- Load In Background：开。
- Preload Audio Data：关。
- 循环由 AudioSource 的 Loop 控制，素材首尾需无爆音。

### 6.5 最小架构

在场景 `Manager` 下建立一个 `AudioManager`，先只保留四个 AudioSource：

1. `MusicSource`：2D、Loop、输出到 Music。
2. `AmbienceSource`：2D、Loop、输出到 Ambience。
3. `SfxSource`：2D、非 Loop、输出到 SFX。
4. `UiSource`：2D、非 Loop、输出到 UI。

当前游戏只有一个 `MainWorld` 场景，通过传送进入竞技场，不需要为了音频再造一个跨场景 `DontDestroyOnLoad` 单例。若编写 `AudioManager.cs`：

- 使用现有场景唯一实例，不再造第二套 GameManager。
- 短音效使用 `AudioSource.PlayOneShot`。
- 不使用 `PlayClipAtPoint` 到处生成临时 GameObject。
- 可提供轻微随机 Pitch（0.95～1.05）给连续砍树/石头，UI 和音乐禁止随机 Pitch。
- 音效为空时只跳过播放，不得报空引用打断游戏。

需要真实位置衰减的树木敲击、箱子、远处敌人，可在对应 Prefab 上单独放 2D/3D 混合 AudioSource；第一版优先使用 2D，避免一开始把空间音频做复杂。

### 6.6 V1.0 音频优先级

P0，必须有：

- UI：按钮点击、打开/关闭背包、商店、箱子。
- 玩家：星尘起手、弹体命中、闪现、受伤、死亡。
- 敌人：剑士挥砍/命中、弓手放箭/箭命中、敌人死亡。
- 世界：拾取、丢弃、砍树、敲石、资源破碎、开箱。
- 战斗：新波提示、胜利、战败。

P1，有时间再加：

- 中土 BGM 1 首。
- 竞技场 BGM 1 首。
- 中土风声/草地环境循环 1 条。
- 脚步与更多随机变体。

P2，V1.0 后：

- 五区域独立环境声、混响、天气、Boss 分层音乐、动态战斗混音。

### 6.7 接入顺序

严格按竖切验证，不要一口气改十几个脚本：

1. Mixer + 四个 AudioSource，先让 UI 点击声播放。
2. 玩家星尘起手和命中。
3. 剑士/弓手攻击与命中。
4. 资源敲击、破碎、拾取。
5. 箱子与面板。
6. 战斗波次/胜负。
7. 最后加入 BGM 和 Ambience，并验证暂停规则。

每完成一步都检查：连续快速触发是否爆音、暂停时是否符合预期、音量是否抢占、Android 真机是否播放。

- `Max Waves = 3`
- 竞技场敌人列表包含黄色剑士和黄色弓手

最新编辑器日志 `test_logs/battle_20260815_061547.txt` 明确记录：

- 06:16:27 第 1 波生成 4 只。
- 06:16:33 第 2 波生成 4 只。
- 06:16:38 第 3 波生成 4 只。
- 清完全部 12 只后正常胜利。

因此不应在没有真机新日志的情况下修改 `BattleManager.Update`、波次计数或死亡计数。旧手机测试“只有一波”更可能来自旧 APK、旧场景配置、用户没有等到间隔结束，或手机端暂停状态没有释放。

### 7.2 正确复测流程

1. Unity 保存 `MainWorld`。
2. 将 Android `Version Code` 从 1 增加到 2，避免误装旧包。
3. 手机卸载旧 APK，再安装新 APK。
4. 进入战斗后不要立即清场退出，至少观察 12 秒。
5. 屏幕应依次出现“第 1/3 波、2/3 波、3/3 波”。
6. 若仍只出现一波，记录当时是否打开过背包/箱子/商店，检查 `Time.timeScale` 是否仍为 0。
7. 用 `adb logcat -s Unity` 收集 `[BM]` 日志；不要仅凭肉眼猜测。

### 7.3 Android 日志隐患

`BattleManager.Awake` 当前把文件日志写到 `Application.dataPath/../test_logs`。编辑器可用，但 Android 安装目录可能不可写。后续若真机控制台出现目录权限异常，才做以下小修：

- Android 使用 `Application.persistentDataPath/test_logs`。
- `Directory.CreateDirectory` 放进 `try/catch`。
- 文件日志失败只发 Warning，不得影响波次逻辑。

不要为了这项日志路径预防性重写整个 BattleManager。

### 7.4 真机仍失败时应增加的最小诊断

只增加一个临时屏幕调试文本或 Debug.Log，显示：

```text
inBattle / waveCount / maxWaves / waveTimer / allWavesSpawned / enemiesAlive / Time.timeScale
```

根据数据判断：

- `waveTimer` 不下降：暂停或 TimeScale 问题。
- `waveCount` 增加但无怪：Prefab 列表、Instantiate 或生成位置问题。
- 三波都生成但玩家只看见一波：生成点、相机范围或敌人立即死亡问题。
- `maxWaves` 真机为 1：打包进去的是旧场景或旧 APK。

## 8. 手机 UI 审计

### 8.1 当前正确项

- Canvas：Screen Space Overlay。
- CanvasScaler：Scale With Screen Size。
- Reference Resolution：1920×1080。
- Match Width Or Height：0.5。
- 手机按钮已连接现有 `OnMobileAttack`、`OnMobileDash` 和交互逻辑。
- `VirtualJoystick` 通过 RectTransform 世界四角计算中心，锚点修好后无需重写。

### 8.2 当前根因

`MobileUI` 自身是居中的 `100×100` RectTransform，所有子按钮再靠巨大位置偏移推到屏幕边缘：

| 控件 | 当前锚点 | 当前位置约值 |
|---|---|---:|
| JoystickBG | 左下 | `(-710, -290)` |
| AttackButton | 右下 | `(710, -290)` |
| DashButton | 右下 | `(886, -466)` |
| InteractButton | 右下 | `(484, -466)` |
| InventoryButton | 右上 | `(886, 466)` |

这套布局只是在 1920×1080 / 16:9 下碰巧对齐。20:9、刘海屏、圆角屏或翻转横屏后会漂移、裁切或重叠。

### 8.3 第一阶段：先修锚点，不写代码

1. 选中 `MobileUI`。
2. Anchor Min 设为 `(0,0)`，Anchor Max 设为 `(1,1)`。
3. Left / Right / Top / Bottom 全部设为 0。
4. Pivot 保持 `(0.5,0.5)`。
5. 逐个重设子控件，不保留原来的 700～886 大偏移。

建议起始值如下，具体手感由用户真机微调：

| 控件 | Anchor | Pivot | Anchored Position | Size |
|---|---|---|---|---|
| JoystickBG | Bottom Left | `(0,0)` | `(60,60)` | `200×200` |
| AttackButton | Bottom Right | `(1,0)` | `(-60,60)` | `200×200` |
| DashButton | Bottom Right | `(1,0)` | `(-280,60)` | `150×150` |
| InteractButton | Bottom Right | `(1,0)` | `(-60,280)` | `150×150` |
| InventoryButton | Top Right | `(1,1)` | `(-60,-60)` | `150×150` |

这些只是稳定起点，不是最终美术尺寸。关键是“相对所属屏幕角落的内边距”，不再是“相对屏幕中心的巨大偏移”。

### 8.4 第二阶段：Safe Area

当前 PlayerSettings 允许渲染到安全区外，但项目没有任何 Safe Area 代码。世界画面可以延伸到刘海外，按钮和 HUD 不可以。

推荐层级：

```text
Canvas
├─ SafeAreaRoot          # Stretch，应用 Screen.safeArea
│  ├─ HUDRoot
│  │  ├─ PlayerHealthBar
│  │  └─ SkillBar
│  └─ MobileUI           # Stretch
│     ├─ JoystickBG
│     ├─ AttackButton
│     ├─ DashButton
│     ├─ InteractButton
│     └─ InventoryButton
├─ InventoryPanel        # 全屏遮罩可留在 Canvas，核心内容再限制安全区
├─ ShopPanel
└─ ChestUI
```

若需要 `SafeAreaFitter.cs`，它只做一件事：读取 `Screen.safeArea`，除以 `Screen.width/height` 转为 0～1 的 Anchor Min/Max，并在分辨率或方向变化时更新。不得修改子按钮位置、大小、颜色或引用。脚本由 AI 写，组件和引用由用户拖。

先修完 8.3 并验证，再增加 Safe Area；两步不要同时做，否则出现偏移时无法判断是哪层造成。

### 8.5 HUD 与面板

- `PlayerHealthBar`、`SkillBar` 应锚在左上安全区，不要继续以中心为基准。
- `InventoryPanel`、`ShopPanel`、`ChestUI` 当前约 `1000×646`，16:9 可用；在 20:9 上通常仍能容纳，但必须检查关闭按钮与边缘是否进入刘海。
- 面板背景可以铺满全屏，真正需要点击的内容和关闭按钮必须落在 Safe Area 内。
- 不要因为长屏就整体拉伸物品格子；背包格子保持方形，空余宽度留给边距。
- 手机端所有面板打开时都必须挡住点击穿透，关闭后恢复输入；不要复制第二套面板。

### 8.6 编辑器测试问题

`GameHUD.Awake` 会在非手机平台自动隐藏 `MobileUI`。为了在编辑器查看布局，不要删除这个判断。可选做法：

- 最简单：在停止运行时直接看 Scene/Game 视图并切不同分辨率。
- 若确实需要 Play Mode 测试，可给 `GameHUD` 增加一个仅用于编辑器的 `showMobileUIInEditor` 序列化开关，并用 `#if UNITY_EDITOR` 限定；默认关闭。

不要把手机 UI 永久显示在 PC 包中。
